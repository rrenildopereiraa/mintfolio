Our CI took eleven minutes. Everyone had a theory. Mine was that the test suite had grown too big, which was wrong, and cost me two days.

The test suite ran in ninety seconds. The other nine and a half minutes were spent rebuilding packages that had not changed.

## Cache hits that weren't

We had a remote cache. It reported a hit rate of about 80%, which sounded healthy enough that nobody looked closer. The number was true and useless: it counted lookups, not work avoided. A package could report a cache hit and still rebuild everything downstream of it, because the hash we stored didn't cover everything the build actually read.

The specific bug was boring. Our hash included the package's own source files and its declared dependencies. It did not include the root `tsconfig.json`. So every branch that touched compiler options invalidated nothing, and every branch that didn't still rebuilt, because a second input we had forgotten about was a timestamp.

```ts
// What we were hashing
const key = hash([...sourceFiles, ...dependencies]);

// What the build actually read
const key = hash([...sourceFiles, ...dependencies, tsconfig, ...envVars]);
```

Once a cache key is wrong in either direction, the cache is worse than no cache: it is a source of confident, incorrect answers.

## Making it answer for itself

The fix that mattered was not the hash. It was making the tool explain itself.

We added a flag that prints, for a given package, exactly which inputs went into its key and which one differed from the last run. The first time we ran it, the answer was a file none of us expected. The second time, a week later, it was an environment variable that a single CI job set and nothing else did.

Both bugs had been there for months. Neither was hard to fix. They were hard to *see*, and a tool that cannot tell you why it made a decision will hide that kind of bug indefinitely.

## Where it landed

CI is now around two minutes forty. Most of that is the test suite, which is the thing that should dominate.

The lesson I keep coming back to is that a cache is a claim about equality, and equality is exactly the thing that is hard to get right. If your build tool can't show its working, you are not measuring your build. You are trusting it.
