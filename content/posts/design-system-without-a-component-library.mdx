The plan was a component library. Six months, one package, every team migrates. We have all seen this plan. It usually produces a package with forty components, eight of which are used.

We did the tokens first instead, mostly because it was the part we could finish in a fortnight.

## What shipped first

One file describing colour, spacing, radii and type. Two build targets: CSS custom properties for the web apps, and a JSON blob for the design tool. A script that failed the build if the two drifted apart.

That was it. No components, no wrapper, nothing to import.

Within a month, four of the six product teams had adopted it, because adopting it meant replacing hex codes with variable names and nothing else. There was no migration, no new dependency to argue about in review, and no version to pin.

## What we learned about components

When we did start building shared components, we built far fewer than planned, and different ones.

The components teams actually wanted were the ones with behaviour that is genuinely hard to get right: a combobox, a date picker, a dialog that manages focus correctly. Nobody wanted a shared `Button`. They wanted the *tokens* for a button, and to write the twelve lines of markup themselves.

That surprised me at the time and seems obvious now. A shared button saves you almost nothing and costs you a negotiation every time a team needs a variant. A shared combobox saves you a fortnight and an accessibility audit.

## The rule we ended up with

Share the thing that is expensive to get right. Publish the values everywhere. Leave the cheap parts alone.

Two years on, the token file has changed a lot and broken nothing, because a rename is a codemod. The component package has eleven things in it. Both numbers feel about right.
